# Apple Paradise Development Context

## Project identity

This repository is the user's personal fork and second-development branch of `linjian-peek-public`, renamed **Apple Paradise / 苹果乐园**.

The product is not an AI model. Its role is to collect device/life facts, maintain current state and long-lived rules, execute local Android actions/reminders, expose state/actions through MCP, and serve as a shared fact layer across multiple AI chat windows.

Canonical product principle:

> 苹果乐园负责记录事实和执行规则，AI负责理解事实和做判断。

When the Notion connector is available, use the master product source of truth:

`🍎 苹果乐园｜完整产品需求与架构存档`

https://app.notion.com/p/3d201fb555898121a658e283cd47376e?pvs=204

Before substantial behavior changes, inspect that requirements page and the existing implementation. Do not silently replace settled product logic with generic best practices.

## Current technical baseline

Preserve the current stack unless the user explicitly requests a migration:

- Android app: Java 11
- Android UI/resources: native Android XML/resources
- Existing manual Android build path
- MCP service: existing Node.js implementation under `mcp/`
- Backend/server: existing server implementation under `server/`

Do **not** introduce Kotlin, Jetpack Compose, Hilt, Room, Navigation3, Gradle convention plugins, or a new framework merely because an external Android skill recommends them.

## Product architecture

Think in three layers:

1. **Device sensing layer** — foreground app, accessibility text/UI nodes, UsageStats, sensors, battery/network, screenshots only when needed, and health data when supported.
2. **Apple Paradise state/execution layer** — Todo, goals, focus, planned/actual time axis, meals, sleep/exercise/life maintenance, wallet, AppGate decisions, rules, reminders, and shared current state.
3. **AI judgment layer** — interpret facts, decide reminders, decide whether app access is appropriate, reschedule, review progress, and choose management intensity.

Do not move judgment-layer behavior into the server unless the rule is explicitly deterministic and meant to be enforced locally.

## Cross-window consistency

Multiple AI windows may operate on the same Apple Paradise instance. Facts or decisions that affect later behavior must therefore be persisted in Apple Paradise rather than only existing in one chat.

Separate:

- long-lived rules/configuration;
- temporary decisions with TTL/expiry;
- bounded operational logs for debugging/conflict tracing.

Expired temporary decisions must not remain effective. A new AI window must not silently invalidate a still-valid explicit decision from another window.

## AppGate / temporary app access

For any AI-facing temporary unlock/allow tool, include a concise instruction equivalent to:

> 请根据用户当前是否确实需要使用该 App、当前任务/专注/日程状态以及苹果乐园中的既有规则判断是否放行；不得仅因用户提出请求就无脑批准临时放行。换聊天窗口不代表原有管理原则失效。

Important:

- The server is not an AI and should not infer subjective need.
- The AI makes contextual judgments.
- The backend may enforce deterministic hard constraints and protect still-valid explicit decisions.
- Do not over-engineer this into a large policy engine unless a concrete bug proves it is necessary.
- A one-time temporary access request is not a long-term policy change.

## `get_current_context`

Treat `get_current_context` as the primary AI decision snapshot. It should expose current decision-relevant facts, not dump the full database.

Expected areas, as available:

- local time/date;
- foreground app/device state;
- effective AppGate locks/allows and expiry/reason;
- Todo/goal status;
- active/recent focus;
- today's phone usage summary;
- meals/life state;
- health summary with source/freshness;
- wallet day/month summary;
- current/next schedule blocks;
- factual attention items;
- per-module freshness/source metadata.

History belongs in dedicated module queries.

## Schedule / time axis

The time axis is not just a traditional calendar. Keep **planned** and **actual** time blocks distinct.

Requirements:

- week/day views;
- vertical time axis;
- category-colored blocks;
- Todo ↔ Schedule ↔ Focus linkage;
- actual blocks may be generated by focus/health/AI/manual sources;
- **actual blocks are always editable by the user**;
- manual edits must not be silently overwritten by later sync;
- retain source/provenance for auto-generated actual blocks.

## Life-maintenance reminders

Life-maintenance items include sleep, shower, hair wash, mopping, sheet changes, and similar recurring maintenance.

Preferred model:

`maintenance rule -> generate concrete schedule instance -> local Android notification -> complete/snooze/reschedule/skip -> actual record -> recalculate next due`

The reminder must be reliable locally on Android and must not depend on ChatGPT being open. Favor a simple, reliable first implementation over complex scheduling intelligence.

## Health

Prefer automated facts over manual logging when technically possible. Do not claim a Huawei/Health Connect field is supported until verified.

Health data should retain source, updated timestamp, and freshness/staleness.

## Wallet

Distinguish:

- `created_at`: when the record was entered;
- `occurred_at` / `transaction_at`: when the spending actually happened.

Support true day-level ledger views, not only month grouping.

## Screen observation

Preferred escalation:

1. current context/state;
2. accessibility text;
3. UI nodes;
4. fresh screenshot only when needed.

Do not build continuous screenshot surveillance unless explicitly requested.

## UI/accessibility baseline

Apple Paradise should look like a coherent mobile app, not a long settings/tool list. Homepage information should emphasize current life state. The time-axis page must use real spatial time layout, not a simple event list.

For interactive UI:

- use understandable labels/content descriptions;
- keep decorative images quiet for accessibility;
- interactive touch targets should generally be at least 48dp;
- keep focus order logical;
- expose stateful control state;
- do not rely only on color to communicate state.

## Privacy/security

This app may handle sensitive phone and life data.

- request only permissions required for concrete features;
- do not log secrets, tokens, passwords, screenshots, health data, or precise location unnecessarily;
- never commit credentials, API keys, signing secrets, or private tokens;
- validate external input;
- keep MCP/server actions narrow and explicit;
- avoid retaining transient sensitive data forever.

## Coding workflow

For each task:

1. inspect the existing implementation and adjacent code first;
2. identify the smallest compatible change;
3. preserve unrelated behavior;
4. do not introduce a new architecture solely to satisfy a generic skill;
5. update Android, server, and MCP together only when the feature truly crosses those boundaries;
6. keep backward compatibility with existing stored state where practical;
7. make migrations explicit when data format changes;
8. compile/test the narrowest affected path;
9. verify Android runtime behavior when device behavior matters;
10. document known limitations rather than hiding them.
